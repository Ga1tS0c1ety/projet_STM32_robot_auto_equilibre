	\section{Cahier des charges}
	
	\subsection*{Objectif général}
	
	Construire un robot auto-équilibré basé sur une carte STM32F4, capable de se stabiliser, de se déplacer et, à terme, d'évoluer vers une navigation autonome.
	
	\subsection*{Version 1 -- Stabilisation de base}
	
	Le robot doit :
	
	\begin{itemize}
		\item tenir debout en équilibre ;
		\item avancer ;
		\item reculer ;
		\item être contrôlé par une boucle temps réel ;
		\item exploiter une IMU pour estimer son inclinaison ;
		\item utiliser des moteurs avec encodeurs pour mesurer le mouvement.
	\end{itemize}
	
	\subsection*{Version 2 -- Robot connecté}
	
	Ajouter :
	
	\begin{itemize}
		\item Wi-Fi via ESP32 ;
		\item télémétrie vers PC ;
		\item réglage des paramètres PID à distance ;
		\item contrôle manuel depuis une interface distante.
	\end{itemize}
	
	\subsection*{Version 3 -- Navigation autonome}
	
	Ajouter :
	
	\begin{itemize}
		\item navigation d'un point A vers un point B ;
		\item estimation de déplacement par odométrie ;
		\item évitement d'obstacles ;
		\item planification de trajectoire simple.
	\end{itemize}
	
	\subsection*{Contraintes de conception}
	
	\begin{itemize}
		\item privilégier l'apprentissage progressif ;
		\item valider chaque brique séparément avant intégration ;
		\item garder une architecture logicielle claire ;
		\item documenter chaque séance ;
		\item éviter d'ajouter des fonctionnalités avancées avant stabilisation.
	\end{itemize}

	\subsection*{Séance 1 -- GPIO}
	
	\begin{sessionbox}
		
		\textbf{Date :} Juillet 2026
		
		\vspace{0.3cm}
		
		\textbf{Objectif :}
		
		Faire clignoter la LED intégrée de la carte STM32 Nucleo-F446RE afin de valider la première interaction réelle avec le microcontrôleur.
		
		\vspace{0.3cm}
		
		\textbf{Objectif pédagogique :}
		
		Comprendre le principe d'un GPIO non pas comme une simple fonction logicielle, mais comme un périphérique matériel contrôlé par des registres mémoire. L'objectif était aussi de commencer à comprendre la relation entre le processeur, la carte mémoire, les bus internes, les registres et les broches physiques du microcontrôleur.
		
		\vspace{0.3cm}
		
		\textbf{Réalisation :}
		
		\begin{itemize}
			\item Mise en place du dossier de travail de la séance 1.
			\item Création d'un projet STM32 minimal nommé \texttt{allume\_led}.
			\item Mise en place d'un workflow de développement basé sur VS Code, CMake, Ninja, la toolchain \texttt{arm-none-eabi-gcc} et OpenOCD.
			\item Vérification de la détection du ST-Link intégré de la carte Nucleo-F446RE sous Linux.
			\item Compilation réussie du projet en mode \texttt{Debug}.
			\item Écriture d'un programme de clignotement de LED sans HAL, par accès direct aux registres.
			\item Flash du programme sur la STM32 avec OpenOCD.
			\item Validation expérimentale : la LED LD2 reliée à PA5 clignote correctement.
			\item Mise en place d'un fichier \texttt{.gitignore} propre pour éviter de versionner les fichiers générés.
			\item Commit Git et synchronisation du projet avec GitHub.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Choix technique :}
		
		Pour cette séance, le choix a été fait de ne pas utiliser HAL. L'objectif n'était pas seulement d'obtenir un résultat fonctionnel, mais de comprendre le fonctionnement interne du microcontrôleur. Le programme a donc été écrit en manipulant directement les adresses mémoire et les registres nécessaires.
		
		\vspace{0.3cm}
		
		\textbf{Problèmes rencontrés :}
		
		\begin{itemize}
			\item Le bouton \textit{Launch STM32CubeMX} de l'extension VS Code ne trouvait pas STM32CubeMX, car STM32CubeMX n'était pas installé ou pas présent dans le chemin système.
			\item Le projet créé était un projet minimal et non un projet STM32Cube/HAL.
			\item La première configuration CMake échouait car Ninja n'était pas installé.
			\item La compilation échouait ensuite car la toolchain ARM \texttt{arm-none-eabi-gcc} n'était pas disponible dans le \texttt{PATH}.
			\item Certaines fonctions graphiques avancées de l'extension STM32 pour VS Code n'étaient pas directement disponibles car le projet n'était pas reconnu comme un projet STM32Cube complet.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Solutions trouvées :}
		
		\begin{itemize}
			\item Utilisation du terminal comme workflow principal pour compiler et flasher le programme.
			\item Installation de Ninja, CMake et de la toolchain ARM.
			\item Compilation avec \texttt{cmake --preset Debug} puis \texttt{cmake --build --preset Debug}.
			\item Flash de la carte avec OpenOCD via l'interface ST-Link.
			\item Décision de conserver ce premier projet comme projet pédagogique minimal, centré sur la compréhension des registres et du fonctionnement matériel.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Notions comprises :}
		
		\begin{itemize}
			\item Un GPIO est un périphérique matériel interne au microcontrôleur.
			\item Le processeur ne commande pas directement une LED : il écrit dans des registres mémoire.
			\item La STM32 utilise le principe du \textit{Memory-Mapped I/O} : les périphériques sont accessibles à travers des adresses mémoire.
			\item \texttt{GPIOA\_BASE} représente l'adresse de base du périphérique GPIOA.
			\item Les registres d'un périphérique sont situés à des offsets fixes à partir de son adresse de base.
			\item Le registre \texttt{MODER} configure le mode des broches GPIO.
			\item Le registre \texttt{ODR} permet de modifier l'état logique des sorties.
			\item Avant d'utiliser GPIOA, il faut activer son horloge via le registre \texttt{RCC\_AHB1ENR}.
			\item AHB signifie \textit{Advanced High-performance Bus}. C'est un bus interne rapide reliant le processeur à certains périphériques.
			\item Le mot-clé \texttt{volatile} est essentiel pour empêcher le compilateur d'optimiser les accès aux registres matériels.
			\item Les opérations binaires comme le décalage, le masquage et le XOR permettent de modifier précisément certains bits d'un registre.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Explication synthétique du fonctionnement :}
		
		Le processeur Cortex-M4 écrit dans le registre d'activation d'horloge du RCC afin d'activer le périphérique GPIOA. Ensuite, il configure la broche PA5 en sortie en modifiant les deux bits correspondants dans le registre \texttt{MODER}. Une fois PA5 configurée en sortie, le programme inverse régulièrement le bit 5 du registre \texttt{ODR}. Cette modification logique se traduit matériellement par un changement de tension sur la broche PA5, ce qui provoque l'allumage puis l'extinction de la LED LD2.
		
		\vspace{0.3cm}
		
		\textbf{Méthode d'apprentissage retenue :}
		
		La méthode retenue pour la suite du projet est de comprendre chaque périphérique avant de l'utiliser. Pour chaque nouvelle brique, il faudra identifier le rôle du périphérique, sa position dans la carte mémoire, ses registres principaux, puis écrire le code correspondant. Le but n'est pas seulement d'utiliser une bibliothèque, mais d'apprendre à lire la documentation constructeur et à raisonner directement sur l'architecture du microcontrôleur.
		
		\vspace{0.3cm}
		
		\textbf{Résultat :}
		
		La LED LD2 de la carte Nucleo-F446RE clignote correctement. La chaîne complète de développement est validée : édition du code, compilation, génération de l'exécutable, flash avec ST-Link et exécution sur la carte.
		
		\vspace{0.3cm}
		
		\textbf{Apprentissage principal :}
		
		Le processeur ne commande jamais directement une LED. Il écrit dans des registres mémoire, et ce sont les périphériques matériels qui transforment ces écritures en actions physiques.
		
		\vspace{0.3cm}
		
		\textbf{Prochaine étape :}
		
		Commencer la séance 2 avec l'UART afin de mettre en place un premier outil de debug série. Cette étape permettra d'afficher des messages depuis la STM32 vers le PC et de mieux observer l'état interne du programme pendant les essais.
		
	\end{sessionbox}
	
	
	%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
	\subsection*{Séance 2 -- UART}
	
	\begin{sessionbox}
		
		\textbf{Date :} Juillet 2026
		
		\vspace{0.3cm}
		
		\textbf{Objectif :}
		
		Mettre en place une liaison série entre la STM32 Nucleo-F446RE et le PC afin de disposer d'une console de debug simple, fiable et réutilisable pendant tout le projet.
		
		\vspace{0.3cm}
		
		\textbf{Objectif pédagogique :}
		
		Comprendre comment un périphérique UART est configuré en accès direct aux registres : activation des horloges, configuration d'une broche en fonction alternative, choix du débit, activation de l'émetteur et envoi des données caractère par caractère.
		
		\vspace{0.3cm}
		
		\textbf{Configuration retenue :}
		
		\begin{itemize}
			\item périphérique : \texttt{USART2} ;
			\item broche d'émission : \texttt{PA2} ;
			\item fonction alternative : \texttt{AF7} ;
			\item débit : 115200 bauds ;
			\item format : 8 bits de données, aucune parité, 1 bit de stop, soit \texttt{115200 8N1} ;
			\item terminal Linux : \texttt{picocom} sur \texttt{/dev/ttyACM0}.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Réalisation :}
		
		\begin{itemize}
			\item Activation de l'horloge de \texttt{GPIOA} dans \texttt{RCC\_AHB1ENR}.
			\item Activation de l'horloge de \texttt{USART2} dans \texttt{RCC\_APB1ENR}.
			\item Configuration de \texttt{PA2} en mode fonction alternative dans \texttt{GPIOA\_MODER}.
			\item Sélection de la fonction \texttt{AF7} dans \texttt{GPIOA\_AFRL} afin de relier physiquement \texttt{PA2} à \texttt{USART2\_TX}.
			\item Configuration du registre \texttt{USART2\_BRR} avec la valeur \texttt{0x8B} pour obtenir environ 115200 bauds à partir d'une horloge de 16 MHz.
			\item Activation de l'émetteur avec le bit \texttt{TE} puis activation du périphérique avec le bit \texttt{UE} dans \texttt{USART2\_CR1}.
			\item Écriture de la fonction \texttt{uart\_send\_char()} qui attend le bit \texttt{TXE} avant d'écrire dans le registre \texttt{USART2\_DR}.
			\item Écriture de la fonction \texttt{uart\_send\_string()} pour transmettre une chaîne caractère par caractère jusqu'au caractère terminal \texttt{'\textbackslash 0'}.
			\item Écriture de la fonction \texttt{uart\_send\_uint()} pour convertir un entier non signé en caractères décimaux sans utiliser \texttt{printf()}.
			\item Utilisation d'une temporisation simple basée sur une boucle et l'instruction \texttt{nop} pour espacer les messages.
			\item Compilation avec CMake, flash avec OpenOCD et observation des messages dans \texttt{picocom}.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Résultats obtenus :}
		
		Le premier test a permis d'afficher correctement :
		
		\begin{center}
			\texttt{Hello Robot}
		\end{center}
		
		Le programme a ensuite été enrichi afin d'afficher une suite de messages numérotés :
		
		\begin{center}
			\texttt{Message numero 1}\\
			\texttt{Message numero 2}\\
			\texttt{Message numero 3}
		\end{center}
		
		La chaîne complète de communication a ainsi été validée :
		
		\begin{center}
			STM32 $\rightarrow$ USART2 $\rightarrow$ PA2 $\rightarrow$ ST-Link $\rightarrow$ USB $\rightarrow$ \texttt{/dev/ttyACM0} $\rightarrow$ \texttt{picocom}
		\end{center}
		
		\vspace{0.3cm}
		
		\textbf{Organisation logicielle :}
		
		Le code UART a été séparé du programme principal afin de commencer à construire une architecture modulaire :
		
		\begin{center}
			\begin{tabular}{l}
				\texttt{Core/Inc/uart.h} : déclarations de l'interface publique ;\\
				\texttt{Core/Src/uart.c} : configuration des registres et fonctions d'émission ;\\
				\texttt{Core/Src/main.c} : logique principale de l'application.
			\end{tabular}
		\end{center}
		
		Le fichier \texttt{main.c} ne manipule donc plus directement les registres de l'USART. Il utilise uniquement les fonctions \texttt{uart\_init()}, \texttt{uart\_send\_char()}, \texttt{uart\_send\_string()} et \texttt{uart\_send\_uint()}.
		
		\vspace{0.3cm}
		
		\textbf{Choix concernant \texttt{printf()} :}
		
		La redirection de \texttt{printf()} vers l'UART a volontairement été reportée. L'objectif de cette séance était de comprendre les mécanismes fondamentaux de transmission et la conversion manuelle des nombres, sans masquer le fonctionnement derrière la bibliothèque standard.
		
		\vspace{0.3cm}
		
		\textbf{Problèmes rencontrés :}
		
		\begin{itemize}
			\item Le terminal série \texttt{picocom} n'était pas initialement installé sur le système.
			\item Le message \texttt{Hello Robot} n'est envoyé qu'une fois au démarrage : si le terminal est ouvert après l'exécution du programme, le message n'est pas visible.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Solutions trouvées :}
		
		\begin{itemize}
			\item Installation de \texttt{picocom} puis ouverture du port avec la commande \texttt{picocom -b 115200 /dev/ttyACM0}.
			\item Appui sur le bouton \texttt{RESET} de la carte après l'ouverture du terminal afin de relancer le programme et de recevoir le message initial.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Notions comprises :}
		
		\begin{itemize}
			\item \texttt{TX} correspond à la transmission et \texttt{RX} à la réception.
			\item Une communication UART est asynchrone : les deux équipements doivent utiliser le même débit et le même format de trame.
			\item Une broche en fonction alternative est pilotée par un périphérique matériel et non directement par le registre \texttt{ODR} du GPIO.
			\item Le débit est défini par le registre \texttt{BRR} à partir de la fréquence d'horloge du périphérique.
			\item Le bit \texttt{TXE} indique que le registre de transmission peut recevoir un nouveau caractère.
			\item Le registre \texttt{DR} contient la donnée à transmettre.
			\item Une chaîne de caractères est un tableau terminé par \texttt{'\textbackslash 0'}.
			\item Un entier doit être converti en caractères avant de pouvoir être affiché dans un terminal.
			\item La séparation entre interface \texttt{.h}, implémentation \texttt{.c} et programme principal rend le code plus lisible et réutilisable.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Apprentissage principal :}
		
		L'UART transforme les données écrites par le processeur dans des registres en une suite de bits transmise sur une broche physique. Grâce à cette liaison, le programme embarqué peut rendre visible son état interne sur le PC.
		
		\vspace{0.3cm}
		
		\textbf{Prochaine étape :}
		
		Utiliser cette console UART pendant la séance 3 pour afficher le résultat de la première communication I2C avec le MPU6050, notamment la valeur de son registre d'identification \texttt{WHO\_AM\_I}.
		
	\end{sessionbox}

	\subsection*{Séance 3 -- IMU : première communication}
	
	\begin{sessionbox}
		
		\textbf{Date :} Juillet 2026
		
		\vspace{0.3cm}
		
		\textbf{Objectif :}
		
		Établir une première communication I2C entre la STM32 Nucleo-F446RE et le module MPU6050, puis vérifier l'identité du capteur en lisant son registre \texttt{WHO\_AM\_I}.
		
		\vspace{0.3cm}
		
		\textbf{Objectif pédagogique :}
		
		Comprendre le chemin complet d'une communication avec un capteur numérique : câblage électrique, configuration des broches en fonction alternative, activation du périphérique I2C, réglage des temporisations, émission d'une adresse, gestion des acquittements et lecture d'un registre interne.
		
		\vspace{0.3cm}
		
		\textbf{Configuration retenue :}
		
		\begin{itemize}
			\item périphérique STM32 : \texttt{I2C1} ;
			\item ligne d'horloge : \texttt{PB8 / I2C1\_SCL} ;
			\item ligne de données : \texttt{PB9 / I2C1\_SDA} ;
			\item fonction alternative : \texttt{AF4} ;
			\item mode électrique : sorties \textit{open-drain} avec résistances de tirage ;
			\item fréquence de l'horloge APB1 : 16 MHz ;
			\item fréquence du bus I2C : 100 kHz ;
			\item adresse I2C du MPU6050 : \texttt{0x68} ;
			\item registre d'identification : \texttt{WHO\_AM\_I} à l'adresse interne \texttt{0x75} ;
			\item valeur attendue : \texttt{0x68}, soit 104 en décimal.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Câblage réalisé :}
		
		\begin{center}
			\begin{tabular}{>{\bfseries}p{4cm}p{4cm}p{4cm}}
				\toprule
				Nucleo-F446RE & Broche STM32 & MPU6050 \\
				\midrule
				3,3 V & Alimentation & VCC \\
				GND & Masse commune & GND \\
				D15 & PB8 / I2C1\_SCL & SCL \\
				D14 & PB9 / I2C1\_SDA & SDA \\
				\bottomrule
			\end{tabular}
		\end{center}
		
		Le module s'est correctement allumé après le câblage. Cette LED confirme la présence de l'alimentation, mais elle ne suffit pas à prouver que les échanges I2C fonctionnent.
		
		\vspace{0.3cm}
		
		\textbf{Réalisation :}
		
		\begin{itemize}
			\item Configuration de \texttt{PB8} et \texttt{PB9} en mode fonction alternative dans \texttt{GPIOB\_MODER}.
			\item Sélection de la fonction \texttt{AF4} dans \texttt{GPIOB\_AFRH} afin de relier les broches au périphérique \texttt{I2C1}.
			\item Configuration des deux lignes en sorties \textit{open-drain}, avec vitesse élevée et résistances de tirage internes.
			\item Activation de l'horloge de \texttt{GPIOB} dans \texttt{RCC\_AHB1ENR}.
			\item Activation de l'horloge de \texttt{I2C1} dans \texttt{RCC\_APB1ENR} avec le bit \texttt{I2C1EN}.
			\item Configuration du champ \texttt{FREQ} de \texttt{I2C1\_CR2} avec la valeur 16, correspondant à une horloge APB1 de 16 MHz.
			\item Configuration du registre \texttt{CCR} avec la valeur 80 afin d'obtenir un bus I2C à 100 kHz en mode standard.
			\item Configuration du registre \texttt{TRISE} avec la valeur 17 pour tenir compte du temps de montée maximal des lignes en mode standard.
			\item Activation du périphérique grâce au bit \texttt{PE} du registre \texttt{I2C1\_CR1}.
			\item Écriture d'une fonction \texttt{i2c1\_probe()} générant une condition \texttt{START}, envoyant l'adresse \texttt{0x68} et vérifiant la réception d'un acquittement \texttt{ACK}.
			\item Écriture d'une fonction \texttt{i2c1\_read\_register()} permettant de sélectionner un registre interne, de produire un \textit{Repeated START}, puis de recevoir un octet.
			\item Lecture du registre \texttt{WHO\_AM\_I} et affichage de sa valeur dans \texttt{picocom} grâce au pilote UART de la séance 2.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Calcul des temporisations :}
		
		Le champ \texttt{FREQ} reçoit la fréquence APB1 exprimée en MHz :
		
		\begin{center}
			\texttt{CR2.FREQ = 16}
		\end{center}
		
		En mode standard, la valeur de \texttt{CCR} est calculée par :
		
		\begin{center}
			\texttt{CCR = 16 000 000 / (2 $\times$ 100 000) = 80}
		\end{center}
		
		Pour le temps de montée maximal de 1~\textmu s, une horloge de 16 MHz représente 16 cycles de 62,5 ns. Le registre est donc programmé avec :
		
		\begin{center}
			\texttt{TRISE = 16 + 1 = 17}
		\end{center}
		
		\vspace{0.3cm}
		
		\textbf{Séquence de lecture de \texttt{WHO\_AM\_I} :}
		
		\begin{center}
			\fbox{\parbox{0.92\textwidth}{
					\centering
					\texttt{START}
					$\rightarrow$ \texttt{0x68 + écriture}
					$\rightarrow$ \texttt{ACK}
					$\rightarrow$ \texttt{registre 0x75}
					$\rightarrow$ \textit{Repeated START}
					$\rightarrow$ \texttt{0x68 + lecture}
					$\rightarrow$ \texttt{ACK}
					$\rightarrow$ \texttt{donnée reçue}
					$\rightarrow$ \texttt{NACK + STOP}
			}}
		\end{center}
		
		La première adresse, \texttt{0x68}, sélectionne le composant présent sur le bus. L'adresse \texttt{0x75} sélectionne ensuite un registre précis à l'intérieur de ce composant. Ces deux adresses ne jouent donc pas le même rôle.
		
		\vspace{0.3cm}
		
		\textbf{Résultats obtenus :}
		
		Le premier test d'adressage a produit :
		
		\begin{center}
			\texttt{Test de l'adresse I2C 0x68...}\\
			\texttt{MPU6050 detecte a l'adresse 0x68}
		\end{center}
		
		La lecture du registre d'identification a ensuite produit :
		
		\begin{center}
			\texttt{Lecture du registre WHO\_AM\_I...}\\
			\texttt{WHO\_AM\_I = 104 en decimal}\\
			\texttt{MPU6050 correctement identifie}
		\end{center}
		
		La valeur 104 en décimal correspond à \texttt{0x68} en hexadécimal. Elle confirme que le composant répond à l'adresse prévue et renvoie l'identifiant attendu.
		
		\vspace{0.3cm}
		
		\textbf{Problèmes rencontrés :}
		
		\begin{itemize}
			\item Lors de la première compilation, les fonctions \texttt{uart\_init()} et \texttt{uart\_send\_string()} étaient déclarées mais introuvables pendant l'édition des liens.
			\item Le fichier \texttt{uart.c} était présent dans le dossier \texttt{Src}, mais il n'était pas ajouté explicitement aux sources du projet dans \texttt{CMakeLists.txt}.
			\item Le registre \texttt{TRISE} affichait initialement la valeur 2 au lieu de 17, car la fonction de configuration n'était pas effectivement appelée avant la lecture du registre.
			\item Une opération automatique de refactorisation proposée par VS Code tentait d'ajouter le fichier d'en-tête \texttt{i2c.h} de manière inadaptée dans \texttt{add\_executable()}.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Solutions trouvées :}
		
		\begin{itemize}
			\item Ajout explicite de \texttt{Src/uart.c} puis de \texttt{Src/i2c.c} dans \texttt{target\_sources()} du fichier \texttt{CMakeLists.txt}.
			\item Reconfiguration et recompilation propre du projet avec CMake et Ninja.
			\item Vérification directe de la valeur de \texttt{TRISE} avant et après l'écriture, ce qui a permis d'identifier l'appel manquant.
			\item Annulation de la proposition de refactorisation automatique et modification manuelle du fichier CMake.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Organisation logicielle :}
		
		Après validation du prototype dans \texttt{main.c}, le pilote I2C a été séparé afin de conserver une architecture claire :
		
		\begin{center}
			\begin{tabular}{>{\bfseries}p{4cm}p{9cm}}
				\toprule
				Fichier & Rôle \\
				\midrule
				\texttt{Inc/i2c.h} & Interface publique : initialisation, test d'adresse et lecture d'un registre. \\
				\texttt{Src/i2c.c} & Registres RCC/GPIO/I2C, fonctions internes de configuration et transactions I2C. \\
				\texttt{Src/main.c} & Initialisation générale, test du MPU6050 et messages de diagnostic UART. \\
				\bottomrule
			\end{tabular}
		\end{center}
		
		Les fonctions internes de configuration sont déclarées \texttt{static}, car elles appartiennent uniquement au pilote. Les fonctions \texttt{i2c1\_init()}, \texttt{i2c1\_probe()} et \texttt{i2c1\_read\_register()} constituent l'interface publique utilisée par le programme principal.
		
		\vspace{0.3cm}
		
		\textbf{Notions comprises :}
		
		\begin{itemize}
			\item La STM32 joue le rôle de maître et génère l'horloge sur \texttt{SCL}.
			\item \texttt{SDA} est une ligne bidirectionnelle utilisée pour les adresses, les données et les acquittements.
			\item Une sortie \textit{open-drain} peut forcer une ligne à zéro ou la relâcher ; la remontée à l'état haut est assurée par une résistance de tirage.
			\item L'adresse I2C du périphérique et l'adresse d'un registre interne sont deux informations différentes.
			\item L'adresse I2C \texttt{0x68} est codée sur 7 bits ; le contrôleur ajoute ensuite le bit lecture/écriture dans l'octet transmis.
			\item Un \texttt{ACK} confirme que le destinataire a reconnu l'adresse ou reçu un octet.
			\item Le bit \texttt{AF} signale au contraire un défaut d'acquittement.
			\item La lecture d'un registre utilise généralement une phase d'écriture pour sélectionner le registre, puis une phase de lecture introduite par un \textit{Repeated START}.
			\item Les bits d'état \texttt{SB}, \texttt{ADDR}, \texttt{TXE}, \texttt{BTF} et \texttt{RXNE} permettent de suivre l'avancement matériel de la transaction.
			\item Des temporisations logicielles évitent de bloquer indéfiniment le processeur lorsqu'un événement I2C ne se produit pas.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Résultat final :}
		
		La chaîne complète est validée : la STM32 configure I2C1, contacte le MPU6050 à l'adresse \texttt{0x68}, sélectionne le registre \texttt{WHO\_AM\_I}, reçoit la valeur \texttt{0x68} et l'affiche sur le terminal série.
		
		\begin{center}
			\fbox{\parbox{0.88\textwidth}{
					\centering
					Cortex-M4 $\rightarrow$ RCC $\rightarrow$ GPIOB/AF4 $\rightarrow$ I2C1 $\rightarrow$ PB8/PB9 $\rightarrow$ MPU6050 $\rightarrow$ UART $\rightarrow$ PC
			}}
		\end{center}
		
		\vspace{0.3cm}
		
		\textbf{Apprentissage principal :}
		
		Avant d'utiliser les mesures d'un capteur dans un algorithme, il faut d'abord valider séparément son alimentation, son câblage, son adresse, ses transactions et son identité. Une communication correctement diagnostiquée devient une base fiable pour les étapes suivantes.
		
		\vspace{0.3cm}
		
		\textbf{Prochaine étape :}
		
		Commencer la séance 4 avec la génération d'un signal PWM à l'aide d'un timer STM32. La lecture des données brutes de l'accéléromètre et du gyroscope sera abordée plus tard, pendant la séance 7.
		
	\end{sessionbox}

	\subsection*{Séance 4 -- PWM moteur}
	
	\begin{sessionbox}
		
		\textbf{Date :} Août 2026
		
		\vspace{0.3cm}
		
		\textbf{Objectif :}
		
		Générer un signal PWM matériel avec un timer de la STM32 Nucleo-F446RE, faire varier son rapport cyclique de 0 à 100~\% et valider expérimentalement la tension moyenne obtenue sur une broche.
		
		\vspace{0.3cm}
		
		\textbf{Objectif pédagogique :}
		
		Comprendre comment un timer transforme une horloge interne en un signal périodique : division de fréquence avec le prescaler, comptage jusqu'à une valeur maximale, comparaison avec un registre de capture/compare et routage du signal vers une broche configurée en fonction alternative.
		
		\vspace{0.3cm}
		
		\textbf{Configuration retenue :}
		
		\begin{itemize}
			\item timer : \texttt{TIM3} ;
			\item canal PWM : \texttt{TIM3\_CH1} ;
			\item broche de sortie : \texttt{PA6} ;
			\item fonction alternative : \texttt{AF2} ;
			\item horloge du timer considérée : 16 MHz ;
			\item prescaler : \texttt{PSC = 15} ;
			\item auto-reload : \texttt{ARR = 999} ;
			\item fréquence PWM obtenue : 1 kHz ;
			\item rapport cyclique réglable avec \texttt{CCR1} ;
			\item mode de sortie : PWM mode 1.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Réalisation :}
		
		\begin{itemize}
			\item Activation de l'horloge de \texttt{GPIOA} dans \texttt{RCC\_AHB1ENR}.
			\item Activation de l'horloge de \texttt{TIM3} dans \texttt{RCC\_APB1ENR}.
			\item Configuration de \texttt{PA6} en mode fonction alternative dans \texttt{GPIOA\_MODER}.
			\item Sélection de \texttt{AF2} dans \texttt{GPIOA\_AFRL} afin de relier \texttt{PA6} à \texttt{TIM3\_CH1}.
			\item Configuration de la sortie en \textit{push-pull}, sans résistance de tirage.
			\item Arrêt du timer pendant sa configuration avec le bit \texttt{CEN}.
			\item Programmation de \texttt{PSC = 15} afin de diviser 16 MHz par 16 et d'obtenir un compteur à 1 MHz.
			\item Programmation de \texttt{ARR = 999} afin d'obtenir une période de 1000 coups de compteur, soit un signal à 1 kHz.
			\item Configuration du canal 1 en PWM mode 1 avec le champ \texttt{OC1M = 110}.
			\item Activation du preload de \texttt{CCR1} avec \texttt{OC1PE} et du preload de \texttt{ARR} avec \texttt{ARPE}.
			\item Activation de la sortie du canal avec le bit \texttt{CC1E} du registre \texttt{CCER}.
			\item Génération d'un événement de mise à jour avec le bit \texttt{UG} afin de charger immédiatement \texttt{PSC}, \texttt{ARR} et \texttt{CCR1}.
			\item Création de la fonction \texttt{pwm\_set\_duty()} pour convertir un pourcentage compris entre 0 et 100 en une valeur de \texttt{CCR1}.
			\item Séparation du pilote dans \texttt{Inc/pwm.h} et \texttt{Src/pwm.c}.
			\item Affichage des informations de test avec le pilote UART bare-metal, sans utiliser \texttt{printf()}.
			\item Réalisation d'un test automatique faisant évoluer le rapport cyclique de 0 à 100~\%, puis de 100 à 0~\%, par pas de 10~\%.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Calcul de la fréquence PWM :}
		
		La fréquence du compteur est donnée par :
		
		\begin{center}
			\texttt{f\_compteur = 16 000 000 / (15 + 1) = 1 000 000 Hz}
		\end{center}
		
		Le compteur parcourt ensuite les valeurs de 0 à 999, soit 1000 états :
		
		\begin{center}
			\texttt{f\_PWM = 1 000 000 / (999 + 1) = 1 000 Hz}
		\end{center}
		
		La période du signal vaut donc 1 ms.
		
		\vspace{0.3cm}
		
		\textbf{Calcul du rapport cyclique :}
		
		\begin{center}
			\texttt{rapport cyclique = CCR1 / (ARR + 1)}
		\end{center}
		
		Pour 60~\% :
		
		\begin{center}
			\texttt{CCR1 = (999 + 1) $\times$ 60 / 100 = 600}
		\end{center}
		
		En PWM mode 1, la sortie reste active lorsque \texttt{CNT < CCR1}, puis devient inactive lorsque \texttt{CNT >= CCR1}.
		
		\vspace{0.3cm}
		
		\textbf{Organisation logicielle :}
		
		\begin{center}
			\begin{tabular}{>{\bfseries}p{4cm}p{9cm}}
				\toprule
				Fichier & Rôle \\
				\midrule
				\texttt{Inc/pwm.h} & Interface publique : initialisation du PWM et réglage du rapport cyclique. \\
				\texttt{Src/pwm.c} & Adresses mémoire, registres GPIO/RCC/TIM3 et implémentation du pilote. \\
				\texttt{Src/main.c} & Initialisation générale, test automatique et messages de diagnostic UART. \\
				\bottomrule
			\end{tabular}
		\end{center}
		
		Le programme principal utilise uniquement \texttt{pwm\_init()} et \texttt{pwm\_set\_duty()}. Il ne manipule plus directement les registres de \texttt{TIM3}.
		
		\vspace{0.3cm}
		
		\textbf{Résultats affichés dans \texttt{picocom} :}
		
		\begin{center}
			\texttt{Demarrage du robot}\\
			\texttt{Initialisation du PWM...}\\
			\texttt{PWM TIM3\_CH1 actif sur PA6}\\
			\texttt{Frequence : 1000 Hz}\\
			\texttt{Rapport cyclique : 60 \%}
		\end{center}
		
		\vspace{0.3cm}
		
		\textbf{Validation au multimètre :}
		
		Le multimètre a été placé entre \texttt{PA6} et la masse de la carte. Il mesure la valeur moyenne du signal PWM.
		
		\begin{center}
			\begin{tabular}{>{\bfseries}p{3.8cm}p{4cm}p{4cm}}
				\toprule
				Rapport cyclique & Valeur théorique & Valeur mesurée \\
				\midrule
				0~\% & 0 V & 0 V \\
				25~\% & 0,825 V & 0,826 V \\
				60~\% & 1,980 V & 1,983 V \\
				100~\% & environ 3,3 V & 3,306 V \\
				\bottomrule
			\end{tabular}
		\end{center}
		
		Les valeurs mesurées sont très proches des valeurs théoriques. Elles confirment que la fonction \texttt{pwm\_set\_duty()} modifie correctement \texttt{CCR1} et que le signal est bien routé vers \texttt{PA6}.
		
		\vspace{0.3cm}
		
		\textbf{Test automatique :}
		
		\begin{center}
			\fbox{\parbox{0.82\textwidth}{
					\centering
					0~\% $\rightarrow$ 10~\% $\rightarrow$ 20~\% $\rightarrow \cdots \rightarrow$ 100~\%
					$\rightarrow$ 90~\% $\rightarrow \cdots \rightarrow$ 0~\%
			}}
		\end{center}
		
		Une temporisation approximative maintient chaque valeur suffisamment longtemps pour observer la montée puis la descente de la tension moyenne au multimètre.
		
		\vspace{0.3cm}
		
		\textbf{Point de vigilance concernant la boucle descendante :}
		
		La variable de boucle descendante est signée. Une variable non signée ne peut pas devenir négative : après zéro, une soustraction provoquerait un débordement et pourrait rendre la boucle infinie.
		
		\vspace{0.3cm}
		
		\textbf{Notions comprises :}
		
		\begin{itemize}
			\item Le PWM est un signal numérique périodique, et non une véritable tension analogique variable.
			\item Le prescaler \texttt{PSC} règle la vitesse du compteur.
			\item Le registre \texttt{ARR} fixe la période du signal.
			\item Le registre \texttt{CCR1} fixe la durée de l'état actif et donc le rapport cyclique.
			\item Le compteur parcourt les valeurs de 0 à \texttt{ARR}, ce qui représente \texttt{ARR + 1} états.
			\item En PWM mode 1, la sortie est active tant que \texttt{CNT < CCR1}.
			\item Les bits de preload permettent d'appliquer les nouvelles valeurs proprement au début d'une période.
			\item Une fonction alternative relie la sortie matérielle d'un timer à une broche physique.
			\item Le multimètre affiche la tension moyenne du PWM, mais il ne montre ni les fronts ni la fréquence exacte du signal.
			\item La STM32 ne devra pas alimenter directement un moteur : le signal PWM commandera plus tard le driver de puissance TB6612FNG.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Résultat final :}
		
		\begin{center}
			\fbox{\parbox{0.88\textwidth}{
					\centering
					Cortex-M4 $\rightarrow$ RCC $\rightarrow$ TIM3 $\rightarrow$ comparaison \texttt{CNT/CCR1}
					$\rightarrow$ \texttt{TIM3\_CH1} $\rightarrow$ AF2 $\rightarrow$ PA6
			}}
		\end{center}
		
		Le pilote génère un signal à 1 kHz dont le rapport cyclique peut être réglé de 0 à 100~\%. Les mesures expérimentales obtenues sont conformes aux calculs.
		
		\vspace{0.3cm}
		
		\textbf{Apprentissage principal :}
		
		Un timer matériel permet de produire un signal précis sans demander au processeur de basculer continuellement une broche. Le processeur configure la fréquence et le rapport cyclique, puis le périphérique timer génère lui-même le signal.
		
		\vspace{0.3cm}
		
		\textbf{Limite volontaire de la séance :}
		
		Le driver TB6612FNG et les moteurs n'ont pas été connectés pendant cette séance. Leur commande par PWM et GPIO de direction sera traitée pendant la séance 6.
		
		\vspace{0.3cm}
		
		\textbf{Prochaine étape :}
		
		Commencer la séance 5 avec les encodeurs afin de mesurer le mouvement réel des moteurs avant l'intégration complète du driver de puissance.
		
	\end{sessionbox}

	\subsection*{Séance 5 -- Encodeurs}
	
	\begin{sessionbox}
		
		\textbf{Date :} Août 2026
		
		\vspace{0.3cm}
		
		\textbf{Objectif :}
		
		Mesurer le mouvement réel d'un motoréducteur à l'aide de son encodeur quadrature, déterminer son sens de rotation, convertir le comptage en position angulaire puis calculer sa vitesse réelle en tours par minute.
		
		\vspace{0.3cm}
		
		\textbf{Objectif pédagogique :}
		
		Comprendre qu'un timer STM32 peut être utilisé autrement que comme base de temps ou générateur PWM. En mode encodeur, le compteur du timer n'est plus principalement cadencé par le temps : il évolue en fonction des transitions reçues sur les deux voies A et B. La séance vise aussi à distinguer clairement mesure de position, mesure de temps et calcul de vitesse.
		
		\vspace{0.3cm}
		
		\textbf{Configuration retenue :}
		
		\begin{itemize}
			\item encodeur quadrature : voies A et B du motoréducteur ;
			\item timer encodeur : \texttt{TIM2} ;
			\item voie A : \texttt{PA0 / TIM2\_CH1} ;
			\item voie B : \texttt{PA1 / TIM2\_CH2} ;
			\item fonction alternative : \texttt{AF1} ;
			\item mode du timer : Encoder mode 3, avec \texttt{SMS = 011} ;
			\item compteur : \texttt{TIM2\_CNT}, utilisé comme compteur signé côté logiciel ;
			\item plage : \texttt{ARR = 0xFFFFFFFF} ;
			\item base de temps indépendante : \texttt{TIM5} ;
			\item horloge considérée pour TIM5 : 16 MHz ;
			\item \texttt{TIM5\_PSC = 15}, soit un compteur à 1 MHz et un tick de 1~\textmu s ;
			\item période d'échantillonnage de la vitesse : environ 100 ms ;
			\item calibration retenue : \textbf{3881 comptes par tour de l'axe de sortie}.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Principe de l'encodeur quadrature :}
		
		Les deux sorties A et B sont des signaux numériques déphasés. L'ordre dans lequel leurs états changent permet de déterminer le sens de rotation. Dans un sens, la séquence des états peut être vue comme :
		
		\begin{center}
			\texttt{00 $\rightarrow$ 10 $\rightarrow$ 11 $\rightarrow$ 01 $\rightarrow$ 00}
		\end{center}
		
		et dans l'autre sens comme la séquence inverse :
		
		\begin{center}
			\texttt{00 $\rightarrow$ 01 $\rightarrow$ 11 $\rightarrow$ 10 $\rightarrow$ 00}
		\end{center}
		
		Le timer observe matériellement les transitions de \texttt{TI1} et \texttt{TI2}. Selon leur ordre, il incrémente ou décrémente automatiquement \texttt{TIM2\_CNT}. Le programme C n'exécute donc pas lui-même \texttt{compteur++} ou \texttt{compteur--} à chaque front.
		
		\vspace{0.3cm}
		
		\textbf{Chemin matériel validé :}
		
		\begin{center}
			\fbox{\parbox{0.90\textwidth}{
					\centering
					Encodeur A/B
					$\rightarrow$ PA0/PA1
					$\rightarrow$ AF1
					$\rightarrow$ TIM2\_CH1/TIM2\_CH2
					$\rightarrow$ TI1/TI2
					$\rightarrow$ logique quadrature
					$\rightarrow$ \texttt{TIM2\_CNT}
			}}
		\end{center}
		
		\vspace{0.3cm}
		
		\textbf{Configuration de TIM2 :}
		
		\begin{itemize}
			\item Activation de l'horloge de \texttt{GPIOA} dans \texttt{RCC\_AHB1ENR}.
			\item Configuration de \texttt{PA0} et \texttt{PA1} en fonction alternative dans \texttt{GPIOA\_MODER}.
			\item Sélection de \texttt{AF1} dans \texttt{GPIOA\_AFRL} afin de relier PA0 à \texttt{TIM2\_CH1} et PA1 à \texttt{TIM2\_CH2}.
			\item Activation de l'horloge de \texttt{TIM2} avec \texttt{TIM2EN} dans \texttt{RCC\_APB1ENR}.
			\item Configuration de \texttt{CC1S = 01} et \texttt{CC2S = 01} dans \texttt{TIM2\_CCMR1} afin de connecter les entrées \texttt{IC1} et \texttt{IC2} à \texttt{TI1} et \texttt{TI2}.
			\item Polarité normale des deux entrées avec \texttt{CC1P = 0} et \texttt{CC2P = 0} dans \texttt{TIM2\_CCER}.
			\item Sélection du mode encodeur 3 avec \texttt{SMS = 011} dans \texttt{TIM2\_SMCR}.
			\item Utilisation de toute la plage 32 bits avec \texttt{TIM2\_ARR = 0xFFFFFFFF}.
			\item Initialisation de \texttt{TIM2\_CNT} à zéro.
			\item Démarrage du compteur avec le bit \texttt{CEN} de \texttt{TIM2\_CR1}.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Organisation logicielle :}
		
		\begin{center}
			\begin{tabular}{>{\bfseries}p{4cm}p{9cm}}
				\toprule
				Fichier & Rôle \\
				\midrule
				\texttt{Inc/encoder.h} & Interface publique : initialisation, lecture du compteur et calcul de vitesse. \\
				\texttt{Src/encoder.c} & Registres GPIO/RCC/TIM2, configuration du mode encodeur et conversions liées au mouvement. \\
				\texttt{Inc/timebase.h} & Interface de la base de temps en microsecondes. \\
				\texttt{Src/timebase.c} & Configuration de TIM5 comme chronomètre matériel à 1~\textmu s par tick. \\
				\texttt{Src/main.c} & Échantillonnage, calcul de $\Delta CNT$, calcul de $\Delta t$ et affichage UART. \\
				\bottomrule
			\end{tabular}
		\end{center}
		
		\vspace{0.3cm}
		
		\textbf{Premier test de position :}
		
		Le moteur n'a pas été alimenté pendant le premier essai. L'axe a été tourné à la main afin de vérifier uniquement l'encodeur. Le compteur est resté stable lorsque l'axe était immobile, a augmenté dans un sens et diminué dans l'autre.
		
		Extraits représentatifs :
		
		\begin{center}
			\texttt{Position : 336}\\
			\texttt{Position : 336}\\
			\texttt{Position : 691}\\
			\texttt{Position : 520}\\
			\texttt{Position : 202}\\
			\texttt{Position : -14}\\
			\texttt{Position : -241}\\
			\texttt{Position : -746}
		\end{center}
		
		Ces essais valident simultanément la réception des deux voies, le comptage matériel et la détection du sens de rotation.
		
		\vspace{0.3cm}
		
		\textbf{Calibration expérimentale :}
		
		Pour convertir le compteur en grandeur physique, plusieurs mesures de dix tours complets de l'axe de sortie ont été réalisées :
		
		\begin{center}
			\begin{tabular}{>{\bfseries}p{3.5cm}p{4.5cm}p{4.5cm}}
				\toprule
				Essai & Comptes pour 10 tours & Comptes par tour \\
				\midrule
				1 & 38826 & 3882,6 \\
				2 & 38809 & 3880,9 \\
				3 & 38809 & 3880,9 \\
				\bottomrule
			\end{tabular}
		\end{center}
		
		La moyenne expérimentale vaut environ 3881,47 comptes par tour. Pour garder une constante simple dans le code, la valeur retenue est :
		
		\begin{center}
			\Large\textbf{3881 comptes/tour}
		\end{center}
		
		Cette calibration est utilisée pour toutes les conversions suivantes.
		
		\vspace{0.3cm}
		
		\textbf{Conversion en angle :}
		
		Un tour complet correspond à 360 degrés. L'angle cumulé de l'axe peut donc être estimé par :
		
		\begin{center}
			$\theta = \frac{CNT}{3881} \times 360^\circ$
		\end{center}
		
		Ainsi, environ 1940 comptes correspondent à un demi-tour, soit environ 180 degrés. Le signe du compteur indique le sens de rotation.
		
		\vspace{0.3cm}
		
		\textbf{Création d'une vraie base de temps :}
		
		Une temporisation logicielle approximative n'est pas adaptée au calcul d'une vitesse. Un deuxième timer, \texttt{TIM5}, a donc été configuré comme chronomètre matériel indépendant de TIM2.
		
		Avec une horloge de 16 MHz et \texttt{PSC = 15} :
		
		\begin{center}
			\texttt{f\_CNT = 16 000 000 / (15 + 1) = 1 000 000 Hz}
		\end{center}
		
		Chaque incrément de \texttt{TIM5\_CNT} représente alors 1~\textmu s. Le registre \texttt{EGR} est utilisé avec le bit \texttt{UG} afin de charger immédiatement la valeur du prescaler avant le démarrage du compteur.
		
		Le test de la base de temps a montré une augmentation continue de \texttt{TIM5\_CNT}, validant le fonctionnement du chronomètre matériel.
		
		\vspace{0.3cm}
		
		\textbf{Calcul de la vitesse :}
		
		Deux positions sont lues à deux instants différents :
		
		\begin{center}
			$\Delta CNT = CNT_{actuel} - CNT_{precedent}$
		\end{center}
		
		\begin{center}
			$\Delta t = t_{actuel} - t_{precedent}$
		\end{center}
		
		La vitesse en tours par minute est ensuite calculée avec :
		
		\begin{center}
			$RPM = \frac{\Delta CNT \times 60 \times 1\,000\,000}{3881 \times \Delta t_{\mu s}}$
		\end{center}
		
		Le calcul est effectué environ toutes les 100 ms. La condition utilise \texttt{delta\_us >= 100000} et non une égalité stricte, car le processeur n'est pas garanti de lire exactement la valeur 100000.
		
		\vspace{0.3cm}
		
		\textbf{Choix d'un calcul entier :}
		
		Une première version du calcul utilisait des nombres flottants. Pendant les essais bare-metal, l'exécution s'arrêtait précisément au moment du calcul de la vitesse en \texttt{float}. Afin de conserver cette séance simple et indépendante d'une configuration supplémentaire de la FPU, le calcul a été réécrit en arithmétique entière.
		
		Le numérateur est calculé en \texttt{int64\_t} afin d'éviter un débordement lors du produit :
		
		\begin{center}
			\texttt{delta\_count $\times$ 60 $\times$ 1 000 000}
		\end{center}
		
		Le résultat final est retourné en \texttt{int32\_t}. Les décimales sont volontairement perdues, ce qui est suffisant pour la validation de cette séance. La configuration et l'utilisation de la FPU seront traitées lorsque les calculs flottants deviendront réellement nécessaires, notamment pour le filtrage et le contrôle.
		
		\vspace{0.3cm}
		
		\textbf{Résultats de vitesse :}
		
		Les essais à la main ont produit des valeurs cohérentes dans les deux sens. Lorsque l'axe est immobile, la variation vaut zéro et la vitesse affichée est nulle. En rotation, le signe de la vitesse suit le signe de $\Delta CNT$.
		
		\begin{center}
			\texttt{Position : 43932 | Delta : 0 | Vitesse : 0 tr/min}\\
			\texttt{Position : 42581 | Delta : -249 | Vitesse : -38 tr/min}\\
			\texttt{Position : 40824 | Delta : -363 | Vitesse : -56 tr/min}\\
			\texttt{Position : 39076 | Delta : 171 | Vitesse : 26 tr/min}\\
			\texttt{Position : 39700 | Delta : 213 | Vitesse : 32 tr/min}\\
			\texttt{Position : 38812 | Delta : 0 | Vitesse : 0 tr/min}
		\end{center}
		
		Ces mesures montrent correctement l'arrêt, l'accélération, le ralentissement et l'inversion du sens de rotation.
		
		\vspace{0.3cm}
		
		\textbf{Conversion future en distance et en vitesse linéaire :}
		
		Si une roue de diamètre $D$ est montée sur l'axe, sa circonférence vaut $\pi D$. En l'absence de glissement :
		
		\begin{center}
			$d = \frac{CNT}{3881} \times \pi D$
		\end{center}
		
		et, si $D$ est exprimé en mètres, la vitesse linéaire vaut :
		
		\begin{center}
			$v = \frac{\pi D \times RPM}{60}$
		\end{center}
		
		Cette relation constituera plus tard la base de l'odométrie du robot.
		
		\vspace{0.3cm}
		
		\textbf{Problèmes rencontrés :}
		
		\begin{itemize}
			\item Confusion initiale sur le rôle du timer en mode encodeur : il fallait le voir ici comme un compteur matériel piloté par les fronts A/B et non comme un simple découpage du temps.
			\item Le premier programme de vitesse affichait les messages d'initialisation puis plus rien.
			\item Le test isolé de TIM5 a confirmé que la base de temps fonctionnait correctement.
			\item Des traces UART placées étape par étape ont montré que le blocage apparaissait après le calcul de $\Delta CNT$, au moment du calcul flottant des RPM.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Solutions trouvées :}
		
		\begin{itemize}
			\item Décomposition du problème en tests séparés : TIM2 pour le mouvement, TIM5 pour le temps, puis combinaison des deux.
			\item Instrumentation du programme avec des messages UART afin de localiser précisément le point de blocage.
			\item Remplacement du calcul \texttt{float} par un calcul entier utilisant \texttt{int64\_t} pour les produits intermédiaires.
			\item Conservation d'une période réelle mesurée avec TIM5 au lieu de supposer que la boucle logicielle dure exactement 100 ms.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Notions comprises :}
		
		\begin{itemize}
			\item Un encodeur quadrature utilise deux voies déphasées afin de mesurer le déplacement et son sens.
			\item Les fronts montants et descendants constituent les événements qui font évoluer le compteur en mode encodeur.
			\item Un même périphérique timer peut servir à des fonctions très différentes selon sa configuration : PWM, base de temps ou interface encodeur.
			\item \texttt{CCMR1} choisit comment les canaux sont utilisés, \texttt{SMCR} sélectionne le mode encodeur, \texttt{CCER} règle la polarité et \texttt{CR1.CEN} démarre le compteur.
			\item Le processeur configure le timer, mais le comptage des fronts est ensuite effectué matériellement.
			\item Une position est une valeur cumulée de compteur, alors qu'une vitesse dépend de la variation de cette position pendant un intervalle de temps.
			\item Une calibration expérimentale sur plusieurs tours réduit l'erreur liée au positionnement manuel.
			\item Le signe de $\Delta CNT$ permet de conserver l'information de sens dans la vitesse.
			\item Une vraie base de temps matérielle est nécessaire pour obtenir une mesure de vitesse fiable.
			\item L'arithmétique entière 64 bits permet de réaliser des calculs précis sans dépendre immédiatement de la FPU.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Résultat final :}
		
		\begin{center}
			\fbox{\parbox{0.92\textwidth}{
					\centering
					Rotation mécanique
					$\rightarrow$ Encodeur A/B
					$\rightarrow$ TIM2
					$\rightarrow$ \texttt{CNT}
					$\rightarrow$ position / angle
					\\[0.2cm]
					\texttt{CNT} + TIM5
					$\rightarrow$ $\Delta CNT / \Delta t$
					$\rightarrow$ vitesse en tr/min
			}}
		\end{center}
		
		La STM32 mesure désormais automatiquement la position relative et le sens de rotation du moteur, puis calcule sa vitesse réelle à partir d'une base de temps matérielle indépendante.
		
		\vspace{0.3cm}
		
		\textbf{Apprentissage principal :}
		
		Le PWM de la séance précédente permettait de commander une action sans savoir exactement ce que le moteur faisait. L'encodeur ferme la chaîne de mesure : il transforme le mouvement mécanique réel en information numérique exploitable par le microcontrôleur.
		
		\vspace{0.3cm}
		
		\textbf{Prochaine étape :}
		
		Commencer la séance 6 avec le driver TB6612FNG afin de commander réellement le moteur en avant et en arrière avec GPIO + PWM, tout en conservant l'encodeur comme retour de mesure.

		\textbf{Objectif :}
		
		Commander réellement un motoréducteur avec le driver TB6612FNG, contrôler son sens de rotation et sa puissance avec GPIO + PWM, puis vérifier la cohérence de la commande à l'aide de l'encodeur.
		
		\vspace{0.3cm}
		
		\textbf{Objectif pédagogique :}
		
		Comprendre le rôle d'un pont en H comme interface entre la logique 3,3 V de la STM32 et la puissance nécessaire au moteur. La séance vise aussi à séparer clairement trois fonctions : l'activation du driver avec \texttt{STBY}, le choix du sens avec \texttt{AIN1/AIN2} et le réglage de la commande moteur avec \texttt{PWMA}. Enfin, les mesures de la séance 5 sont réutilisées afin de comparer la commande PWM au mouvement réellement observé.

		\textbf{Configuration retenue :}
		
		\begin{itemize}
			\item driver moteur : \texttt{TB6612FNG}, canal A ;
			\item \texttt{PC0} $\rightarrow$ \texttt{AIN1} ;
			\item \texttt{PC1} $\rightarrow$ \texttt{AIN2} ;
			\item \texttt{PC2} $\rightarrow$ \texttt{STBY} ;
			\item \texttt{PA6 / TIM3\_CH1} $\rightarrow$ \texttt{PWMA} ;
			\item \texttt{AO1/AO2} $\rightarrow$ les deux fils de puissance du moteur ;
			\item logique du TB6612FNG : 3,3 V depuis la STM32 ;
			\item alimentation moteur : environ 5 V obtenus avec le convertisseur Buck LM2596 ;
			\item masse commune entre STM32, TB6612FNG, Buck et encodeur ;
			\item encodeur conservé sur \texttt{PA0 / TIM2\_CH1} et \texttt{PA1 / TIM2\_CH2} ;
			\item TIM5 conservé comme base de temps pour le calcul de vitesse.

		\vspace{0.3cm}
		
		\textbf{Préparation de l'alimentation :}
		
		La batterie LiPo 2S ne doit pas être utilisée directement comme tension de test du moteur. Le convertisseur Buck LM2596 a donc été placé entre la batterie et l'entrée \texttt{VM} du TB6612FNG. La tension de sortie a été réglée au multimètre à environ 5,0 V avant de connecter le driver.
		
		Le potentiomètre du module étant multi-tours, plusieurs rotations ont été nécessaires avant d'observer une variation visible de la tension. Cette étape a montré l'importance de toujours régler et vérifier la sortie d'un convertisseur avant de l'appliquer au circuit de puissance.
		
		\begin{center}
			\fbox{\parbox{0.90\textwidth}{
					\centering
					LiPo 2S
					$\rightarrow$ Buck LM2596 réglé à 5 V
					$\rightarrow$ \texttt{VM} du TB6612FNG
					$\rightarrow$ \texttt{AO1/AO2}
					$\rightarrow$ moteur
			}}
		\end{center}
		
		La logique reste alimentée séparément :
		
		\begin{center}
			\texttt{STM32 3,3 V $\rightarrow$ VCC du TB6612FNG}
		\end{center}
		
		Les masses de la STM32, du driver et de l'alimentation moteur sont reliées afin que tous les niveaux logiques utilisent la même référence électrique.
		
		\vspace{0.3cm}
		
		\textbf{Principe de commande du canal A :}
		
		Le sens est déterminé par les entrées \texttt{AIN1} et \texttt{AIN2}, tandis que \texttt{PWMA} reçoit le PWM produit pendant la séance 4. La broche \texttt{STBY} doit rester à l'état haut pour autoriser le fonctionnement du driver.
		
		\begin{center}
			\begin{tabular}{>{\bfseries}p{3cm}p{3cm}p{6cm}}
				\toprule
				\texttt{AIN1} & \texttt{AIN2} & Utilisation dans le projet \\
				\midrule
				1 & 0 & Rotation dans le sens appelé \texttt{AVANT}. \\
				0 & 1 & Rotation dans le sens appelé \texttt{ARRIERE}. \\
				0 & 0 & État utilisé lors de l'arrêt logiciel. \\
				\bottomrule
			\end{tabular}
		\end{center}
		
		Le rapport cyclique de \texttt{PWMA} ne choisit donc pas le sens : il règle la commande appliquée au moteur. Les GPIO \texttt{PC0}, \texttt{PC1} et \texttt{PC2} sont configurés en sorties \textit{push-pull}, car la STM32 doit imposer directement des niveaux logiques bas ou hauts au driver.
		
		\vspace{0.3cm}
		
		\textbf{Organisation logicielle :}
		
		Un pilote moteur séparé a été créé afin de ne pas mélanger la logique de direction avec la génération PWM :
		
		\begin{center}
			\begin{tabular}{>{\bfseries}p{4cm}p{9cm}}
				\toprule
				Fichier & Rôle \\
				\midrule
				\texttt{Inc/moteur.h} & Interface publique du pilote moteur. \\
				\texttt{Src/moteur.c} & Configuration de GPIOC et commande de \texttt{AIN1}, \texttt{AIN2} et \texttt{STBY}. \\
				\texttt{Inc/pwm.h / Src/pwm.c} & Génération du PWM sur \texttt{PA6 / TIM3\_CH1}. \\

				\texttt{Src/main.c} & Séquences de test, affichage UART et comparaison PWM / vitesse. \\
				\bottomrule
			\end{tabular}
		\end{center}
		
		Les principales fonctions ajoutées sont :
		
		\begin{itemize}
			\item \texttt{moteur\_init()} ;
			\item \texttt{moteur\_avant()} ;
			\item \texttt{moteur\_arriere()} ;
			\item \texttt{moteur\_arreter()} ;
			\item \texttt{moteur\_activer()} ;
			\item \texttt{moteur\_desactiver()}.
		\end{itemize}

		\begin{center}
			\fbox{\parbox{0.90\textwidth}{
					\centering
					\texttt{moteur.c} $\rightarrow$ direction + activation
					\qquad
					\texttt{pwm.c} $\rightarrow$ commande PWM
			}}
		\end{center}
		
		Le programme principal peut ainsi demander un sens avec \texttt{moteur\_avant()} ou \texttt{moteur\_arriere()}, puis régler le rapport cyclique avec \texttt{pwm\_set\_duty()} sans manipuler directement les registres.

Cette convention est cohérente sur les deux moteurs et peut être conservée ou corrigée plus tard au niveau logiciel selon la convention choisie pour le robot.
		
		\vspace{0.3cm}
		
		\textbf{Vérification du calcul de vitesse :}
		
		À 60~\%, une valeur typique du moteur 1 est d'environ $\Delta CNT = -458$ sur 0,1 s. Avec 3881 comptes par tour :
		
		\begin{center}
			$RPM \approx \frac{-458 \times 60}{3881 \times 0,1} \approx -70,8~\mathrm{tr/min}$
		\end{center}
		
		La valeur calculée est cohérente avec l'affichage UART, proche de -70 tr/min. La chaîne encodeur + TIM2 + TIM5 + calcul entier reste donc valide lorsque le moteur est réellement piloté par le TB6612FNG.
		
		\vspace{0.3cm}
		
		\textbf{Problèmes et observations rencontrés :}
		
		\begin{itemize}
			\item Le réglage du Buck LM2596 semblait initialement ne pas réagir ; son potentiomètre multi-tours nécessitait simplement plusieurs rotations avant de faire varier sensiblement la tension.
			\item Le signe de la vitesse est négatif pour la commande appelée \texttt{AVANT}. Ce comportement n'est pas une erreur : il dépend de l'ordre des voies A/B et de la convention choisie.
			\item Après la suppression de la commande, la position encodeur peut encore évoluer pendant un court instant : le moteur possède une inertie et ne s'immobilise pas instantanément.
			\item Les deux moteurs ne donnent pas exactement la même vitesse pour un même rapport cyclique, ce qui est normal pour des actionneurs réels et sera traité plus tard lors des boucles de contrôle.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Notions comprises :}
		
		\begin{itemize}
			\item La STM32 fournit les signaux de commande, tandis que le TB6612FNG commute l'énergie provenant de l'alimentation moteur.
			\item \texttt{VCC} alimente la logique du driver alors que \texttt{VM} alimente l'étage de puissance moteur.
			\item Une masse commune est nécessaire pour donner une référence électrique commune aux signaux de commande.
			\item \texttt{STBY} active ou désactive le driver.
			\item \texttt{AIN1/AIN2} déterminent le sens de rotation.
			\item \texttt{PWMA} reçoit le signal PWM et règle la commande appliquée au moteur.
			\item Les broches de direction sont utilisées en \textit{push-pull}, contrairement aux lignes I2C configurées en \textit{open-drain}.
			\item Le PWM demandé et la vitesse réelle sont deux grandeurs différentes.
			\item L'encodeur permet d'observer la réponse réelle du moteur et de conserver l'information de sens grâce au signe de $\Delta CNT$.
			\item La vitesse augmente progressivement au démarrage : le moteur possède une dynamique et une inertie.
			\item Deux moteurs identiques peuvent présenter de petites différences de vitesse pour une même commande.
		\end{itemize}
		
		\vspace{0.3cm}
		
		\textbf{Résultat final :}
		
		\begin{center}
			\fbox{\parbox{0.92\textwidth}{
					\centering
					\textbf{Commande :}
					STM32
					$\rightarrow$ \texttt{PC0/PC1/PC2} + \texttt{PA6/TIM3}
					$\rightarrow$ TB6612FNG
					$\rightarrow$ moteur
					\\[0.2cm]
					\textbf{Mesure :}
					moteur
					$\rightarrow$ encodeur A/B
					$\rightarrow$ TIM2
					$\rightarrow$ $\Delta CNT$
					\quad + \quad
					TIM5 $\rightarrow \Delta t$
					$\rightarrow$ vitesse
			}}
		\end{center}
		
		La STM32 sait désormais commander le sens et le niveau de commande d'un moteur à travers le TB6612FNG tout en mesurant simultanément le mouvement réellement obtenu avec l'encodeur.
		
		\vspace{0.3cm}
		
		\textbf{Apprentissage principal :}
		
		Le PWM indique ce que le microcontrôleur demande au moteur ; l'encodeur indique ce que le moteur fait réellement. La séance 6 réunit pour la première fois la chaîne d'action et la chaîne de mesure, sans encore fermer la boucle de contrôle.

	\section{Notions théoriques}
	
	\subsection*{Memory-Mapped I/O : carte mémoire, périphériques et registres}
	
	Dans un microcontrôleur STM32, l'espace d'adressage ne contient pas uniquement la mémoire dans laquelle sont stockées les variables. Une partie des adresses est réservée aux périphériques matériels : GPIO, UART, I2C, timers, ADC ou encore RCC. Ce principe est appelé \textit{Memory-Mapped I/O}.
	
	Pour le processeur, lire ou écrire un registre matériel ressemble donc à lire ou écrire une case mémoire. La différence est que cette opération produit un effet physique ou permet de lire l'état d'un périphérique.
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{4cm}p{9cm}}
			\toprule
			Élément & Signification \\
			\midrule
			Carte mémoire & Organisation de tout l'espace d'adresses vu par le processeur. \\
			Périphérique & Bloc matériel, par exemple GPIOA ou USART2. \\
			Adresse de base & Première adresse réservée au périphérique. \\
			Offset & Position d'un registre par rapport à l'adresse de base. \\
			Registre & Petite zone mémoire, souvent de 32 bits, qui configure ou décrit le périphérique. \\
			Bit ou champ de bits & Partie précise d'un registre associée à une fonction. \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	La règle essentielle est :
	
	\begin{center}
		\textbf{Adresse du registre = adresse de base du périphérique + offset du registre}
	\end{center}
	
	Exemple avec GPIOA :
	
	\begin{itemize}
		\item \texttt{GPIOA\_BASE = 0x40020000} ;
		\item l'offset de \texttt{MODER} est \texttt{0x00} ;
		\item l'adresse de \texttt{GPIOA\_MODER} est donc \texttt{0x40020000} ;
		\item l'offset de \texttt{ODR} est \texttt{0x14} ;
		\item l'adresse de \texttt{GPIOA\_ODR} est donc \texttt{0x40020014}.
	\end{itemize}
	
	Exemple avec USART2 :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{3.5cm}p{3cm}p{5cm}}
			\toprule
			Registre & Offset & Rôle principal \\
			\midrule
			\texttt{USART2\_SR} & \texttt{0x00} & Indique l'état du périphérique, par exemple \texttt{TXE}. \\
			\texttt{USART2\_DR} & \texttt{0x04} & Contient la donnée à transmettre ou reçue. \\
			\texttt{USART2\_BRR} & \texttt{0x08} & Configure le débit en bauds. \\
			\texttt{USART2\_CR1} & \texttt{0x0C} & Active et configure les fonctions principales de l'USART. \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	Une définition comme :
	
	\begin{center}
		\texttt{\#define USART2\_DR (*(volatile uint32\_t *)(USART2\_BASE + 0x04UL))}
	\end{center}
	
	peut être comprise en quatre étapes :
	
	\begin{enumerate}
		\item calculer l'adresse du registre avec la base et l'offset ;
		\item considérer cette adresse comme un pointeur vers un entier de 32 bits ;
		\item utiliser \texttt{volatile} pour imposer un véritable accès matériel ;
		\item déréférencer le pointeur avec \texttt{*} pour lire ou modifier le registre.
	\end{enumerate}
	
	\begin{warningbox}
		Une adresse incorrecte ou un mauvais bit peut configurer un autre périphérique ou produire un comportement imprévisible. Les adresses, offsets et positions des bits doivent toujours être vérifiés dans le manuel de référence et la datasheet du microcontrôleur.
	\end{warningbox}
	
	\subsection*{Registres et opérations sur les bits}
	
	Un registre contient plusieurs fonctions indépendantes. Il ne faut donc généralement pas remplacer toute sa valeur lorsqu'on souhaite modifier un seul bit.
	
	Les opérations les plus utilisées sont :
	
	\begin{itemize}
		\item activer un bit : \verb!registre |= (1UL << n)! ;
		\item désactiver un bit : \verb!registre &= ~(1UL << n)! ;
		\item tester un bit : \verb!registre & (1UL << n)! ;
		\item inverser un bit : \verb!registre ^= (1UL << n)! ;
		\item modifier un champ de plusieurs bits : effacer d'abord le champ avec un masque, puis écrire la nouvelle valeur.
	\end{itemize}
	
	Cette méthode permet de modifier uniquement la fonction recherchée sans perturber les autres bits du registre.
	
	\subsection*{RCC et bus internes}
	
	Le RCC, ou \textit{Reset and Clock Control}, distribue les horloges aux différents périphériques. Un périphérique dont l'horloge n'est pas activée ne peut pas fonctionner correctement, même si ses registres sont configurés.
	
	Les périphériques sont reliés au processeur par plusieurs bus internes :
	
	\begin{itemize}
		\item AHB1 pour des périphériques rapides comme les GPIO ;
		\item APB1 pour plusieurs périphériques comme USART2, I2C et certains timers ;
		\item APB2 pour d'autres périphériques rapides comme certains USART et timers.
	\end{itemize}
	
	La démarche habituelle est donc : identifier le bus du périphérique, activer son horloge dans le registre RCC correspondant, puis configurer ses propres registres.
	
	\subsection*{GPIO}
	
	Les GPIO sont des broches numériques configurables. Une broche peut notamment fonctionner comme entrée, sortie, fonction alternative ou entrée analogique. Le registre \texttt{MODER} choisit ce mode.
	
	En sortie GPIO, le programme commande directement le niveau logique grâce au registre \texttt{ODR}. En fonction alternative, la broche est confiée à un autre périphérique matériel, par exemple un USART ou un timer.
	
	Les GPIO seront utilisés pour les LEDs, les boutons, les signaux de direction des moteurs et plusieurs fonctions alternatives.
	
	\subsection*{UART}
	
	L'UART est une communication série asynchrone. Elle utilise principalement une ligne \texttt{TX} pour transmettre et une ligne \texttt{RX} pour recevoir. Comme aucune horloge n'est transmise sur un fil séparé, les deux équipements doivent partager le même débit et le même format de trame.
	
	La configuration \texttt{115200 8N1} signifie : 115200 symboles par seconde, 8 bits de données, aucune parité et 1 bit de stop.
	
	Dans ce projet, USART2 transmet sur PA2. Les registres principaux utilisés sont :
	
	\begin{itemize}
		\item \texttt{BRR} pour le débit ;
		\item \texttt{CR1} pour activer l'émetteur et le périphérique ;
		\item \texttt{SR} pour consulter l'état de la transmission ;
		\item \texttt{DR} pour écrire le caractère à transmettre.
	\end{itemize}
	
	L'UART sert au debug et à la télémétrie. Il permet d'observer les mesures, les états et les erreurs internes du robot depuis un terminal PC.
	
	\subsection*{I2C}
	
	L'I2C, ou \textit{Inter-Integrated Circuit}, est un bus série synchrone utilisé pour relier un contrôleur à un ou plusieurs circuits intégrés. Il utilise seulement deux lignes partagées :
	
	\begin{itemize}
		\item \texttt{SCL}, ou \textit{Serial Clock}, qui transporte l'horloge générée par le maître ;
		\item \texttt{SDA}, ou \textit{Serial Data}, qui transporte les adresses, les données et les acquittements dans les deux directions.
	\end{itemize}
	
	Dans le projet, la STM32 est le maître du bus et le MPU6050 est un périphérique esclave. La STM32 décide du début et de la fin des échanges, génère l'horloge et choisit le composant avec lequel elle souhaite communiquer.
	
	\begin{center}
		\fbox{\parbox{0.82\textwidth}{
				\centering
				STM32 maître $\rightarrow$ \texttt{SCL} + \texttt{SDA} $\rightarrow$ MPU6050 esclave
		}}
	\end{center}
	
	\subsubsection*{Sorties open-drain et résistances de tirage}
	
	Les lignes I2C utilisent un fonctionnement \textit{open-drain}. Un périphérique peut tirer la ligne vers la masse pour produire un zéro logique, mais il ne force pas directement un niveau haut. Pour produire un état logique 1, tous les composants relâchent la ligne et une résistance de tirage la ramène vers 3,3 V.
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{4cm}p{8.5cm}}
			\toprule
			Action électrique & État obtenu \\
			\midrule
			Un composant tire la ligne vers GND & Niveau logique 0 \\
			Tous les composants relâchent la ligne & La résistance de tirage produit le niveau logique 1 \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	Ce principe permet à plusieurs composants de partager les mêmes fils sans qu'un périphérique force un niveau haut pendant qu'un autre force un niveau bas. Les modules MPU6050 possèdent souvent déjà des résistances de tirage, mais leur présence et leur valeur doivent être vérifiées lors de l'intégration matérielle.
	
	\subsubsection*{Adresse du périphérique et adresse du registre}
	
	Deux niveaux d'adressage interviennent lors de la lecture du MPU6050 :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{4.2cm}p{3cm}p{6cm}}
			\toprule
			Information & Exemple & Rôle \\
			\midrule
			Adresse I2C du périphérique & \texttt{0x68} & Sélectionner le MPU6050 parmi les composants présents sur le bus. \\
			Adresse du registre interne & \texttt{0x75} & Sélectionner le registre \texttt{WHO\_AM\_I} à l'intérieur du MPU6050. \\
			Valeur du registre & \texttt{0x68} & Identifier la famille du composant qui a répondu. \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	Connaître l'adresse théorique \texttt{0x68} ne prouve pas que le capteur fonctionne. La lecture de \texttt{WHO\_AM\_I} vérifie en même temps le câblage, la configuration logicielle, l'adressage, l'écriture de l'adresse interne et la réception d'une donnée.
	
	L'adresse I2C du MPU6050 est exprimée sur 7 bits. Lors de la transmission, le contrôleur construit un octet contenant cette adresse dans les bits 7 à 1, puis ajoute le bit lecture/écriture en position 0 :
	
	\begin{center}
		\texttt{adresse transmise = (adresse 7 bits $\ll$ 1) + bit R/W}
	\end{center}
	
	Ainsi, pour l'adresse \texttt{0x68} :
	
	\begin{itemize}
		\item en écriture, l'octet transmis est \texttt{0xD0} ;
		\item en lecture, l'octet transmis est \texttt{0xD1}.
	\end{itemize}
	
	\subsubsection*{START, STOP, ACK et NACK}
	
	Une transaction I2C est structurée par plusieurs événements :
	
	\begin{itemize}
		\item \texttt{START} : le maître prend le contrôle du bus et commence une transaction ;
		\item adresse + bit \texttt{R/W} : le maître choisit le destinataire et indique le sens de l'échange ;
		\item \texttt{ACK} : le récepteur tire SDA à zéro pour confirmer la réception ;
		\item \texttt{NACK} : absence d'acquittement, utilisée pour signaler une erreur ou la fin d'une réception ;
		\item \textit{Repeated START} : nouveau départ sans libérer le bus, utile pour passer d'une phase d'écriture à une phase de lecture ;
		\item \texttt{STOP} : le maître termine l'échange et libère le bus.
	\end{itemize}
	
	Pour lire un registre, la STM32 doit d'abord écrire son adresse interne, puis relancer immédiatement une transaction en lecture :
	
	\begin{center}
		\fbox{\parbox{0.94\textwidth}{
				\centering
				\texttt{START}
				$\rightarrow$ adresse périphérique + écriture
				$\rightarrow$ \texttt{ACK}
				$\rightarrow$ adresse du registre
				$\rightarrow$ \textit{Repeated START}
				$\rightarrow$ adresse périphérique + lecture
				$\rightarrow$ \texttt{ACK}
				$\rightarrow$ donnée
				$\rightarrow$ \texttt{NACK}
				$\rightarrow$ \texttt{STOP}
		}}
	\end{center}
	
	\subsubsection*{Configuration de I2C1 sur STM32F446RE}
	
	Dans la séance 3, \texttt{I2C1} a été configuré avec \texttt{PB8} pour SCL et \texttt{PB9} pour SDA. Ces broches sont placées en fonction alternative \texttt{AF4}, en mode \textit{open-drain}.
	
	Les principaux registres utilisés sont :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{3.5cm}p{9.5cm}}
			\toprule
			Registre & Rôle \\
			\midrule
			\texttt{CR1} & Activation du périphérique et génération de \texttt{START}, \texttt{STOP} et des acquittements. \\
			\texttt{CR2} & Indication de la fréquence de l'horloge APB1 exprimée en MHz. \\
			\texttt{CCR} & Réglage de la période de l'horloge SCL. \\
			\texttt{TRISE} & Prise en compte du temps maximal de montée des lignes. \\
			\texttt{DR} & Envoi de l'adresse, du numéro de registre ou d'une donnée ; réception d'une donnée. \\
			\texttt{SR1} & Événements et erreurs : \texttt{SB}, \texttt{ADDR}, \texttt{BTF}, \texttt{TXE}, \texttt{RXNE}, \texttt{AF}. \\
			\texttt{SR2} & État général du bus, notamment le bit \texttt{BUSY}. \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	Avec une horloge APB1 de 16 MHz et un bus standard à 100 kHz :
	
	\begin{itemize}
		\item \texttt{CR2.FREQ = 16} ;
		\item \texttt{CCR = 16 000 000 / (2 $\times$ 100 000) = 80} ;
		\item \texttt{TRISE = 16 + 1 = 17}.
	\end{itemize}
	
	Le champ \texttt{FREQ} ne reçoit donc pas la fréquence du bus I2C. Il reçoit la fréquence d'entrée du périphérique exprimée en MHz. Le registre \texttt{CCR} utilise ensuite cette information pour produire l'horloge SCL recherchée.
	
	\subsubsection*{Validation progressive}
	
	La communication a été validée en deux étapes :
	
	\begin{enumerate}
		\item \textbf{Test d'adresse :} génération de \texttt{START}, envoi de l'adresse \texttt{0x68} et vérification du bit \texttt{ADDR}. La réponse \texttt{ACK} confirme qu'un composant est présent.
		\item \textbf{Lecture de l'identifiant :} écriture de l'adresse interne \texttt{0x75}, \textit{Repeated START}, lecture d'un octet et vérification de la valeur \texttt{0x68}.
	\end{enumerate}
	
	Des compteurs de temporisation sont utilisés dans les boucles d'attente. Ils empêchent le programme de rester bloqué indéfiniment si le bus est occupé, si la condition \texttt{START} n'est pas générée ou si le périphérique ne répond pas.
	
	\begin{warningbox}
		Une LED allumée sur le module prouve seulement que le circuit reçoit une alimentation. Elle ne confirme ni le câblage de SDA/SCL, ni la bonne adresse, ni la réussite des transactions. La validation logicielle par \texttt{ACK} puis par lecture de \texttt{WHO\_AM\_I} reste indispensable.
	\end{warningbox}
	
	\subsection*{PWM et timers}
	
	Le PWM, ou \textit{Pulse Width Modulation}, est un signal numérique périodique dont on fait varier la largeur de l'impulsion. La sortie alterne rapidement entre un niveau bas et un niveau haut, mais la proportion de temps passée à l'état haut peut être modifiée.
	
	Cette proportion est appelée \textbf{rapport cyclique} :
	
	\begin{center}
		\texttt{D = T\_haut / T\_periode}
	\end{center}
	
	Un rapport cyclique de 0~\% signifie que la sortie reste toujours basse. À 50~\%, elle reste haute pendant la moitié de chaque période. À 100~\%, elle reste toujours haute.
	
	\subsubsection*{Tension moyenne}
	
	Pour un signal compris entre 0 V et 3,3 V, la tension moyenne idéale vaut :
	
	\begin{center}
		\texttt{V\_moyenne = 3,3 $\times$ D}
	\end{center}
	
	Par exemple, avec un rapport cyclique de 60~\% :
	
	\begin{center}
		\texttt{V\_moyenne = 3,3 $\times$ 0,60 = 1,98 V}
	\end{center}
	
	C'est cette valeur moyenne qu'un multimètre en mode tension continue affiche approximativement. Un oscilloscope ou un analyseur logique serait nécessaire pour observer directement les niveaux hauts et bas, la période, la fréquence et la largeur exacte des impulsions.
	
	\subsubsection*{Génération matérielle avec un timer}
	
	La STM32 ne génère pas le PWM en exécutant continuellement des instructions pour mettre une broche à zéro puis à un. Elle configure un timer matériel qui travaille ensuite de manière autonome.
	
	\begin{center}
		\fbox{\parbox{0.88\textwidth}{
				\centering
				Horloge du timer
				$\rightarrow$ \texttt{PSC}
				$\rightarrow$ compteur \texttt{CNT}
				$\rightarrow$ comparaison avec \texttt{CCR1}
				$\rightarrow$ canal \texttt{TIM3\_CH1}
				$\rightarrow$ AF2
				$\rightarrow$ PA6
		}}
	\end{center}
	
	Les registres principaux sont :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{3.5cm}p{9.5cm}}
			\toprule
			Registre & Rôle \\
			\midrule
			\texttt{PSC} & Divise la fréquence d'entrée du timer. La division réelle vaut \texttt{PSC + 1}. \\
			\texttt{CNT} & Contient la valeur courante du compteur. \\
			\texttt{ARR} & Fixe la valeur maximale du compteur et donc la période. \\
			\texttt{CCR1} & Fixe la valeur de comparaison du canal 1 et donc le rapport cyclique. \\
			\texttt{CCMR1} & Configure le mode de sortie du canal, notamment PWM mode 1. \\
			\texttt{CCER} & Active la sortie du canal et règle sa polarité. \\
			\texttt{CR1} & Démarre le compteur et active notamment le preload de \texttt{ARR}. \\
			\texttt{EGR} & Permet de générer un événement de mise à jour avec le bit \texttt{UG}. \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	\subsubsection*{Fréquence du compteur et fréquence PWM}
	
	\begin{center}
		\texttt{f\_compteur = f\_timer / (PSC + 1)}
	\end{center}
	
	\begin{center}
		\texttt{f\_PWM = f\_timer / ((PSC + 1) $\times$ (ARR + 1))}
	\end{center}
	
	Le terme \texttt{ARR + 1} apparaît parce que le compteur parcourt toutes les valeurs de 0 à \texttt{ARR}.
	
	Dans la séance 4 :
	
	\begin{itemize}
		\item \texttt{f\_timer = 16 MHz} ;
		\item \texttt{PSC = 15}, donc le compteur fonctionne à 1 MHz ;
		\item \texttt{ARR = 999}, donc une période contient 1000 coups de compteur ;
		\item \texttt{f\_PWM = 1 000 000 / 1000 = 1000 Hz}.
	\end{itemize}
	
	La période vaut donc 1 ms.
	
	\subsubsection*{Rapport cyclique et registre CCR1}
	
	En PWM mode 1, la sortie est active lorsque \texttt{CNT < CCR1}. Elle devient inactive lorsque le compteur atteint ou dépasse \texttt{CCR1}. Le rapport cyclique idéal est donc :
	
	\begin{center}
		\texttt{D = CCR1 / (ARR + 1)}
	\end{center}
	
	Avec \texttt{ARR = 999} :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{4cm}p{4cm}p{4cm}}
			\toprule
			Rapport cyclique & Valeur de \texttt{CCR1} & Temps haut à 1 kHz \\
			\midrule
			0~\% & 0 & 0~\textmu s \\
			25~\% & 250 & 250~\textmu s \\
			60~\% & 600 & 600~\textmu s \\
			100~\% & 1000 & 1000~\textmu s \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	La fonction du pilote applique directement cette relation :
	
	\begin{center}
		\texttt{CCR1 = ((ARR + 1) $\times$ duty\_percent) / 100}
	\end{center}
	
	Le pourcentage est limité à 100 afin d'empêcher l'écriture d'une commande incohérente.
	
	\subsubsection*{Preload et mise à jour}
	
	Les registres \texttt{ARR} et \texttt{CCR1} peuvent utiliser des registres de preload. Une nouvelle valeur est alors stockée temporairement et appliquée lors du prochain événement de mise à jour. Cela évite de modifier une période en plein milieu et de créer une impulsion irrégulière.
	
	Le bit \texttt{ARPE} active le preload de \texttt{ARR}, tandis que \texttt{OC1PE} active celui de \texttt{CCR1}. Le bit \texttt{UG} du registre \texttt{EGR} force un événement de mise à jour, notamment pour charger immédiatement les valeurs de \texttt{PSC}, \texttt{ARR} et \texttt{CCR1} avant le démarrage.
	
	\subsubsection*{Fonction alternative et sortie physique}
	
	La sortie produite par \texttt{TIM3\_CH1} reste interne au microcontrôleur tant qu'elle n'est pas reliée à une broche. La broche \texttt{PA6} est donc configurée en fonction alternative \texttt{AF2}.
	
	\begin{center}
		\fbox{\parbox{0.82\textwidth}{
				\centering
				Timer configuré
				$\rightarrow$ canal 1 activé
				$\rightarrow$ \texttt{TIM3\_CH1}
				$\rightarrow$ fonction alternative AF2
				$\rightarrow$ sortie physique PA6
		}}
	\end{center}
	
	\subsubsection*{PWM et commande moteur}
	
	Le PWM produit par la STM32 est un signal logique de commande. La broche \texttt{PA6} ne fournit pas directement l'énergie nécessaire au moteur : elle transmet seulement l'information de commande au TB6612FNG.
	
	Depuis la séance 6, la chaîne réellement utilisée est :
	
	\begin{center}
		\fbox{\parbox{0.88\textwidth}{
				\centering
				STM32 / \texttt{TIM3\_CH1} / PA6
				$\rightarrow$ \texttt{PWMA}
				$\rightarrow$ TB6612FNG
				$\rightarrow$ alimentation moteur \texttt{VM}
				$\rightarrow$ \texttt{AO1/AO2}
				$\rightarrow$ moteur
		}}
	\end{center}
	
	Le rapport cyclique détermine le niveau de commande appliqué au moteur. Une augmentation du rapport cyclique entraîne généralement une augmentation de la vitesse, mais le pourcentage de PWM n'est pas égal au pourcentage de la vitesse maximale. Les frottements, la charge, l'alimentation, le réducteur et la dynamique mécanique influencent le résultat réel.
	
	Les essais de la séance 6 l'ont montré directement : pour le premier moteur, des commandes de 20~\%, 40~\%, 60~\% et 80~\% ont conduit respectivement à des vitesses stabilisées d'environ 20, 47, 72--73 et 96--97 tr/min en valeur absolue.
	
	Le PWM représente donc la \textbf{commande}, tandis que l'encodeur fournit la \textbf{mesure réelle}.
	
	\subsubsection*{Pont en H et TB6612FNG}
	
	Un moteur DC change de sens lorsque la polarité appliquée à ses deux bornes est inversée. Le pont en H du TB6612FNG réalise cette inversion électroniquement, sans modifier physiquement les fils du moteur.
	
	Pour le canal A utilisé pendant la séance 6 :
	
	\begin{itemize}
		\item \texttt{AIN1} est reliée à \texttt{PC0} ;
		\item \texttt{AIN2} est reliée à \texttt{PC1} ;
		\item \texttt{STBY} est reliée à \texttt{PC2} ;
		\item \texttt{PWMA} est reliée à \texttt{PA6 / TIM3\_CH1} ;
		\item \texttt{AO1} et \texttt{AO2} sont reliées aux deux fils de puissance du moteur.
	\end{itemize}
	
	La séparation fonctionnelle peut être résumée ainsi :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{4cm}p{8.5cm}}
			\toprule
			Signal & Fonction \\
			\midrule
			\texttt{STBY} & Active ou désactive le driver. \\
			\texttt{AIN1/AIN2} & Déterminent le sens de rotation choisi. \\
			\texttt{PWMA} & Reçoit le PWM et règle le niveau de commande du moteur. \\
			\texttt{AO1/AO2} & Appliquent la puissance commutée aux deux bornes du moteur. \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	Dans la convention logicielle retenue :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{3cm}p{3cm}p{5.5cm}}
			\toprule
			\texttt{AIN1} & \texttt{AIN2} & Commande \\
			\midrule
			1 & 0 & \texttt{moteur\_avant()} \\
			0 & 1 & \texttt{moteur\_arriere()} \\
			0 & 0 & état utilisé par \texttt{moteur\_arreter()} \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	Le changement de sens ne nécessite donc pas de modifier le rapport cyclique. À PWM identique, inverser \texttt{AIN1} et \texttt{AIN2} inverse le sens du moteur.
	
	\subsubsection*{Alimentation logique, alimentation moteur et masse commune}
	
	Le TB6612FNG sépare la partie logique de la partie puissance :
	
	\begin{itemize}
		\item \texttt{VCC} alimente la logique du driver et est reliée au 3,3 V de la STM32 ;
		\item \texttt{VM} alimente l'étage moteur et a été alimentée à environ 5 V pendant les essais ;
		\item les masses de la STM32, du driver et de l'alimentation moteur sont reliées ensemble.
	\end{itemize}
	
	Le convertisseur Buck LM2596 a été utilisé pour abaisser la tension de la LiPo 2S avant de l'appliquer à \texttt{VM}. La sortie du Buck a d'abord été réglée au multimètre, sans moteur connecté, puis vérifiée à environ 5,0 V.
	
	La masse commune est indispensable : un niveau logique de 3,3 V n'a de sens pour le TB6612FNG que si la STM32 et le driver utilisent le même potentiel de référence.
	
	\begin{center}
		\fbox{\parbox{0.90\textwidth}{
				\centering
				LiPo 2S
				$\rightarrow$ Buck 5 V
				$\rightarrow$ \texttt{VM}
				$\rightarrow$ TB6612FNG
				$\rightarrow$ moteur
				\\[0.2cm]
				STM32 3,3 V
				$\rightarrow$ \texttt{VCC}
				\qquad
				GND STM32 = GND TB6612FNG = GND Buck
		}}
	\end{center}
	
	\subsubsection*{Commande et retour de mesure}
	
	La séance 6 réunit deux chaînes jusque-là étudiées séparément :
	
	\begin{center}
		\fbox{\parbox{0.92\textwidth}{
				\centering
				\textbf{Action :}
				STM32
				$\rightarrow$ direction + PWM
				$\rightarrow$ TB6612FNG
				$\rightarrow$ moteur
				\\[0.25cm]
				\textbf{Mesure :}
				moteur
				$\rightarrow$ encodeur A/B
				$\rightarrow$ TIM2
				$\rightarrow$ position
				\quad + \quad
				TIM5 $\rightarrow \Delta t$
				$\rightarrow$ vitesse
		}}
	\end{center}
	
	À PWM constant de 60~\%, l'inversion du sens du moteur provoque aussi l'inversion du signe de $\Delta CNT$ et donc du signe des RPM. Dans le câblage actuel, la commande \texttt{AVANT} produit un comptage négatif et la commande \texttt{ARRIERE} un comptage positif.
	
	Cette distinction entre commande et mesure est fondamentale pour la suite : une future boucle de régulation pourra comparer une consigne de vitesse à la vitesse réellement mesurée puis ajuster automatiquement le PWM. Cette régulation n'est cependant pas réalisée pendant la séance 6.
	
	
	\begin{warningbox}
		Une tension moyenne correcte au multimètre confirme le rapport cyclique de manière indirecte, mais elle ne suffit pas à vérifier précisément la fréquence, les fronts ou d'éventuelles déformations du signal. Une mesure à l'oscilloscope reste la validation la plus complète.
	\end{warningbox}
	\subsection*{Encodeurs}
	
	Un encodeur incrémental transforme une rotation mécanique en une suite de transitions numériques. Dans le projet, les motoréducteurs utilisent un encodeur en quadrature composé de deux voies, A et B, déphasées l'une par rapport à l'autre.
	
	\subsubsection*{Pourquoi deux voies ?}
	
	Avec une seule voie, il est possible de compter des impulsions et donc d'estimer un déplacement. Avec deux voies déphasées, l'ordre des transitions permet en plus de connaître le sens de rotation.
	
	Une rotation peut produire la séquence :
	
	\begin{center}
		\texttt{00 $\rightarrow$ 10 $\rightarrow$ 11 $\rightarrow$ 01 $\rightarrow$ 00}
	\end{center}
	
	Dans l'autre sens, l'ordre est inversé :
	
	\begin{center}
		\texttt{00 $\rightarrow$ 01 $\rightarrow$ 11 $\rightarrow$ 10 $\rightarrow$ 00}
	\end{center}
	
	Le sens n'est donc pas déduit de la valeur instantanée de A ou B prise séparément, mais de la succession des états des deux voies.
	
	\subsubsection*{Timer en mode encodeur}
	
	Sur STM32, un timer peut utiliser directement les deux entrées de capture comme interface encodeur. Dans la séance 5, les voies sont reliées à \texttt{TIM2\_CH1} et \texttt{TIM2\_CH2} :
	
	\begin{center}
		\fbox{\parbox{0.86\textwidth}{
				\centering
				Voie A $\rightarrow$ PA0 / AF1 $\rightarrow$ TIM2\_CH1 / TI1\\
				Voie B $\rightarrow$ PA1 / AF1 $\rightarrow$ TIM2\_CH2 / TI2\\[0.2cm]
				TI1 + TI2 $\rightarrow$ logique quadrature $\rightarrow$ \texttt{TIM2\_CNT}
		}}
	\end{center}
	
	Les registres principaux utilisés sont :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{3.5cm}p{9.5cm}}
			\toprule
			Registre & Rôle \\
			\midrule
			\texttt{CCMR1} & Configure CH1 et CH2 comme entrées reliées à TI1 et TI2. \\
			\texttt{CCER} & Définit notamment la polarité des deux entrées. \\
			\texttt{SMCR} & Sélectionne le mode encodeur avec le champ \texttt{SMS}. \\
			\texttt{CNT} & Contient la position relative courante sous forme de comptes. \\
			\texttt{ARR} & Fixe la plage maximale du compteur. \\
			\texttt{CR1} & Le bit \texttt{CEN} démarre ou arrête le compteur. \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	En mode encodeur, il faut retenir une différence fondamentale avec le PWM :
	
	\begin{center}
		\begin{tabular}{>{\bfseries}p{4cm}p{8.5cm}}
			\toprule
			Utilisation du timer & Ce qui fait évoluer \texttt{CNT} \\
			\midrule
			PWM / base de temps & L'horloge du timer, éventuellement divisée par \texttt{PSC}. \\
			Mode encodeur & Les transitions détectées sur les voies A et B. \\
			\bottomrule
		\end{tabular}
	\end{center}
	
	Le processeur configure donc le périphérique une seule fois, puis le timer compte matériellement les transitions sans qu'une interruption logicielle soit nécessaire pour chaque front.
	
	\subsubsection*{Position, angle et calibration}
	
	La valeur brute de \texttt{CNT} représente des comptes, et non directement des degrés ou des tours. Il faut connaître le nombre de comptes correspondant à un tour complet de l'axe.
	
	Une calibration expérimentale sur trois séries de dix tours a donné une moyenne d'environ 3881,47 comptes par tour. La constante utilisée dans le projet est arrondie à :
	
	\begin{center}
		\texttt{ENCODER\_COUNTS\_PER\_REV = 3881}
	\end{center}
	
	Le nombre de tours cumulés vaut alors :
	
	\begin{center}
		$N_{tours} = \frac{CNT}{3881}$
	\end{center}
	
	et l'angle cumulé :
	
	\begin{center}
		$\theta = \frac{CNT}{3881} \times 360^\circ$
	\end{center}
	
	Cette position est relative au zéro choisi au démarrage. Une rotation dans le sens opposé produit des comptes négatifs lorsqu'ils sont interprétés côté logiciel avec un type signé.
	
	\subsubsection*{Vitesse à partir de la variation de position}
	
	Une valeur unique de \texttt{CNT} ne donne pas la vitesse. Il faut comparer deux lectures séparées dans le temps :
	
	\begin{center}
		$\Delta CNT = CNT_2 - CNT_1$
	\end{center}
	
	\begin{center}
		$\Delta t = t_2 - t_1$
	\end{center}
	
	Avec une base de temps exprimée en microsecondes, la vitesse en tours par minute est calculée par :
	
	\begin{center}
		$RPM = \frac{\Delta CNT \times 60 \times 1\,000\,000}{3881 \times \Delta t_{\mu s}}$
	\end{center}
	
	Le signe de $\Delta CNT$ est conservé : une vitesse positive et une vitesse négative correspondent donc aux deux sens de rotation.
	
	\subsubsection*{Base de temps indépendante avec TIM5}
	
	La temporisation par boucle utilisée lors des premiers tests n'est pas suffisamment précise pour mesurer une vitesse. TIM5 est donc configuré comme chronomètre matériel.
	
	Avec une horloge de 16 MHz et \texttt{PSC = 15} :
	
	\begin{center}
		\texttt{16 MHz / (15 + 1) = 1 MHz}
	\end{center}
	
	Ainsi :
	
	\begin{center}
		\texttt{1 tick TIM5 = 1 \textmu s}
	\end{center}
	
	TIM2 mesure donc le \textbf{mouvement}, tandis que TIM5 mesure le \textbf{temps}. La vitesse est obtenue en combinant les deux informations.
	
	\begin{center}
		\fbox{\parbox{0.88\textwidth}{
				\centering
				TIM2 $\rightarrow$ $\Delta CNT$ \hspace{1cm}
				TIM5 $\rightarrow$ $\Delta t$\\[0.2cm]
				$\Delta CNT + \Delta t \rightarrow$ vitesse en tr/min
		}}
	\end{center}
	
	\subsubsection*{Distance et vitesse linéaire avec une roue}
	
	Si une roue de diamètre $D$ est montée sur l'axe, sa circonférence vaut :
	
	\begin{center}
		$C = \pi D$
	\end{center}
	
	Sans glissement, chaque tour complet déplace théoriquement le robot d'une circonférence. La distance parcourue peut donc être estimée par :
	
	\begin{center}
		$d = \frac{CNT}{3881} \times \pi D$
	\end{center}
	
	Si $D$ est exprimé en mètres, la vitesse linéaire en mètres par seconde est :
	
	\begin{center}
		$v = \frac{\pi D \times RPM}{60}$
	\end{center}
	
	Le facteur 60 est nécessaire parce que les RPM sont exprimés en tours par minute. Ces relations serviront plus tard pour l'odométrie et l'estimation du déplacement du robot.
	
	\begin{warningbox}
		La conversion encodeur $\rightarrow$ distance suppose que la roue roule sans glisser. Sur un robot réel, le patinage, la déformation des pneus et les différences entre les deux moteurs peuvent introduire une erreur d'odométrie. Une calibration expérimentale de chaque roue sera donc préférable lors de l'intégration finale.
	\end{warningbox}
	
	\subsection*{Filtre complémentaire}
	
	L'accéléromètre fournit une estimation de l'inclinaison stable à long terme mais sensible aux vibrations et aux accélérations du robot. Le gyroscope mesure rapidement les variations angulaires mais son intégration dérive progressivement.
	
	Le filtre complémentaire combine les deux informations : le gyroscope décrit principalement les variations rapides, tandis que l'accéléromètre corrige lentement la dérive. Le résultat est une estimation d'angle plus stable pour la boucle d'équilibre.
	
	\subsection*{PID}
	
	Le PID corrige l'erreur entre une consigne et une mesure :
	
	\begin{itemize}
		\item le terme proportionnel réagit à l'erreur actuelle ;
		\item le terme intégral corrige une erreur persistante ;
		\item le terme dérivé anticipe les variations rapides de l'erreur.
	\end{itemize}
	
	Dans ce projet, un PID sera utilisé pour contrôler l'angle du robot et un autre pourra être utilisé pour la vitesse des moteurs. Les gains devront être réglés progressivement afin d'éviter les oscillations et l'instabilité.

	\section{Les erreurs et leçons apprises}
	
	\subsection*{Erreur 1 -- PID instable}
	
	\textbf{Cause possible :} gain proportionnel trop élevé.
	
	\textbf{Solution :} réduire le gain proportionnel puis ajouter progressivement les autres termes.
	
	\textbf{Leçon :} régler P avant I et D.
	
	\subsection*{Erreur 2 -- Robot qui tremble}
	
	\textbf{Cause possible :} bruit IMU, câbles moteurs trop proches des signaux, châssis flexible.
	
	\textbf{Solution :} filtrage, séparation des câbles puissance/signaux, fixation rigide de l'IMU.
	
	\textbf{Leçon :} un problème de stabilité n'est pas toujours un problème de code.
	
	\subsection*{Erreur 3 -- Reset de la STM32}
	
	\textbf{Cause possible :} chute de tension lors de l'appel de courant des moteurs.
	
	\textbf{Solution :} alimentation logique séparée via Buck Converter et masse commune propre.
	
	\textbf{Leçon :} l'alimentation est une partie critique du système.
	
	\subsection*{Erreur 4 -- Réglage du Buck qui semble ne pas réagir}
	
	\textbf{Observation :} pendant la séance 6, la tension de sortie du LM2596 semblait initialement ne pas varier lorsque le potentiomètre était tourné.
	
	\textbf{Cause :} le potentiomètre de réglage est multi-tours ; plusieurs rotations peuvent être nécessaires avant d'observer une variation sensible.
	
	\textbf{Solution :} régler le Buck sans moteur connecté, mesurer en permanence la tension entre \texttt{OUT+} et \texttt{OUT-}, puis arrêter le réglage lorsque la valeur recherchée est atteinte. Pour les essais de la séance 6, la sortie a été réglée à environ 5,0 V.
	
	\textbf{Leçon :} toujours vérifier au multimètre la sortie d'un convertisseur avant de connecter l'étage de puissance.
